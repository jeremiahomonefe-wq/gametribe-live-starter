# Game Tribe Live - starter 0.2

A web-first, realtime multiplayer quiz. It is ready for small live events and pilots, but it is not yet a production-hardened service (see the list below).

## What's implemented in this starter

- Host creates a game and receives a 6-digit PIN.
- Guests join with a nickname and PIN; no account required.
- Host starts the quiz, advances questions, and reveals answers.
- Server owns the game state, question timer, answer acceptance, and scoring.
- One answer per player per question; late answers are rejected.
- Projector/player views update through Socket.IO.
- Player reconnect tokens are generated by the server and stored in the current browser tab session.
- Refreshing or reconnecting can restore the same player identity, score, and submitted-answer state while the server process is still running.
- Disconnected players remain in the game roster and are marked offline; their scores and answers are retained for the session.
- Automated tests cover core game rules, reconnect behavior, the server event layer, quiz rules and CSV import.
- Quiz builder with your own questions and correct answers, plus CSV import and export (details below). Quizzes are saved in the browser.
- Lobby QR code and a copyable join link; the player page has its own address (`/#join=<PIN>`).
- Host recovery: a host who refreshes or drops comes back to the same game.
- One deploy: the Node server serves the built website as well as the game (Dockerfile and `render.yaml` included).

## Not implemented yet

- A server-side database. Games live in server memory and end when the server restarts. Quizzes are stored only in the browser that created them, so they do not follow you to another device or browser.
- Accounts and cloud-saved quizzes, moderation tools (such as removing a player), analytics, payments, and multi-server scaling.
- Results export (a CSV of final scores) and a player-view preview inside the quiz builder.
- Capacity proof on your real hosting. Simulated crowds of up to 1,000 players ran cleanly on one machine (see below), but nothing has been tested on a real hosting plan with real phones and venue networks. Run the load test against your own deployment before promising a number.

## How many players can join?

**Measured (simulated players, one machine, loopback network, one question with everyone answering):**

| Players | Question reaches a player (median) | Answer acknowledged (median) | Data sent for the question | Server CPU* | Server memory |
| --- | --- | --- | --- | --- | --- |
| 100 | 21 ms | 2 ms | about 270 MB before the fix, a few MB after | 4% of a core | 93 MB |
| 300 before the fix | 77 ms | **8,863 ms** | **7,074 MB** | 8% | 150 MB |
| 300 after the fix | 9 ms | 1 ms | 5 MB | 5% | 98 MB |
| 500 | 21 ms | 1 ms | 9 MB | 7% | 116 MB |
| 1,000 (joined in 5 s, answered in 3 s) | 31 ms | 1 ms | 10 MB | 12% | 131 MB |

*Shared with the test program itself, on a single core. No dropped connections or errors in any of these runs.

**What the fix was:** the server used to send the full game state, including every player's score, to every phone after every join and every answer, so the data grew with the cube of the crowd (about 94 KB per message at 500 players). Now each screen gets only what it needs: the host everything, the projector the top 10 and a few names, phones just the question (about 0.4 KB) plus their own score and rank sent privately. Busy updates are batched (at most one per 250 ms per game), while phase changes (start, lock, reveal, next) are never delayed.

**What this does not prove:** real phones, venue Wi-Fi and mobile networks, and your actual hosting plan's CPU were not part of the test. Realistic limits are likely to be the venue network (use mobile data for large crowds rather than one Wi-Fi) and the host's browser (the host receives the full roster; use a laptop for crowds over a few hundred).

**Test your own deployment before an event:**

```
npm run load-test -- --players 300 --url https://<your-server-address>
```

Options: `--join-seconds` (how long the crowd takes to join, default 10) and `--answer-seconds` (default 6). Run it from your own computer so it uses the real internet path, and use a copy of the game server you will use at the event.

## Release 0.2 additions (from the PRD)

- Server locks each question at its deadline (state `locked`), then reveals the answer about 2 seconds later with no host action. The host can still reveal earlier, and always presses Next. Late answers are rejected.
- Answers carry the question index, so an answer for an old question is rejected.
- Host can end the game at any time; answers stop immediately.
- Projector is its own read-only screen. The host button opens `/#projector=<PIN>` in a new tab; it receives public state only and has no host token, so host commands are refused.
- Host dashboard shows how many players have answered. Players see a correct / not this time / no answer result card (sent privately, never in public state).
- Nicknames allow letters, numbers, spaces and `- _ . '`.
- Joining, reconnecting and projector lookups are rate limited per connection (12 attempts per 30 seconds).
- Event handling lives in `server/src/hub.js`, separate from Socket.IO, and is covered by tests.
- After a game every screen has a way out: players get **Back to home** and **Join another game**, the host gets **Back to home** and **Host this quiz again**, and the projector screen has **Back to start**. Leaving clears the saved game, so a refresh does not drag anyone back into it.
- Each screen receives only the state it needs (host, projector, phone), and busy updates are batched, so large crowds stay fast. See "How many players can join?".

## Host recovery and quiz builder

- The host's game PIN and host token are kept in the browser tab. After a refresh or a dropped connection the host reconnects with `host:reconnect` and keeps control of the same game. Players and the projector see "The host lost connection" until then. The game and its timers keep running meanwhile.
- A late close event from an old host connection is ignored, so it cannot mark a returned host offline.
- Host commands are authorised by the host token (a secret only the host's browser holds), not by the connection. A host whose connection dropped and came back keeps control, and any valid command makes the sending connection the current host.
- Quiz builder: create, edit, duplicate and delete quizzes; 2 to 4 answers, one correct answer, a time limit per question, move or duplicate questions. Limits and messages come from `server/src/quiz-rules.js`, shared by the editor and the server, which validates every quiz again before a game starts.
- A live game uses a copy of the quiz taken at launch.
- Quizzes are saved in the browser (localStorage) until accounts and a database exist (PRD 1.0). They do not follow the user to another device.

## The built-in questions

The app ships with 40 ready questions (Bible, Nigeria, general knowledge, cartoons and games). **Host the Game Tribe quiz** on the home screen starts a game with them, and they also appear as the first card in **Build a quiz**, where **Copy to edit** makes your own editable version.

The questions live in the app itself (`server/src/default-quiz.js`), so they never depend on a file, a database or a network request. To change them, edit `docs/default-questions.csv` and run `npm run default-quiz` (add `-- "My title"` to rename it), then rebuild. A test fails if the two ever disagree.

## Import questions from a CSV file

In **Build a quiz**: **Import questions from CSV** creates a new quiz (named after the file) and saves it straight away, so it is in your list for future games. Inside a quiz, **Add from CSV** appends more questions, and **Download CSV** exports the quiz to edit in a spreadsheet. **Download template** gives a ready example (also in `docs/sample-questions.csv`).

| Column | What goes in it |
| --- | --- |
| `question` | The question text |
| `option_a` to `option_d` | 2 to 4 answers. Leave unused ones blank |
| `correct` | `A`, `B`, `C`, `D` (or 1 to 4), or the exact text of the correct answer |
| `seconds` | Time limit, 5 to 120. Blank means 15 |

- Header names are flexible (`Question Text`, `Choice A`, `Correct Answer`, `Time Limit` all work). Comma, semicolon and tab separators are detected.
- In Excel use Save As, then **CSV UTF-8**, so accents and symbols survive.
- Up to 50 questions per quiz and 1 MB per file. Extra rows are left out and the report says so.
- Rows with a problem are still imported, marked in red, so you fix them in the editor instead of losing them. A quiz cannot be hosted until every question is valid.
- Quizzes are stored in the browser for now (see below), so they stay on the device and browser they were imported on.

## Put it online (one deploy)

After `npm run build`, the Node server also serves the website, so players and the game share one address and no cross-origin settings are needed. The lobby shows a QR code and the host can copy a join link.

- **Render (easiest):** push this folder to GitHub, create a new Blueprint or Web Service from it. `render.yaml` is included. Build command `npm install && npm run build`, start command `npm start`. Free plans sleep when idle, so open the site a few minutes before an event.
- **Docker (Fly.io, Railway, any VPS):** `docker build -t gametribe-live .` then `docker run -p 4000:4000 gametribe-live`.
- **Same Wi-Fi, no internet:** `npm install && npm run build && npm start`, then players open `http://<your-laptop-ip>:4000`. Allow the app through the laptop's firewall.
- Run exactly one instance: games live in that server's memory, so a restart ends them.
- Use HTTPS online. Phones and the clipboard features need it, and the QR link uses whatever address the host page was opened on.
- Development is unchanged: `npm run dev` (server on 4000, site on 5173).

## If it says "Cannot reach the server" or "Connection lost"

The app now explains itself: after 4 seconds offline it shows a yellow notice with the server address it is trying and the reason.

- **"Cannot reach the game server" (it never connected):** the address is wrong, the server is off or asleep, or the server does not allow this website. Press **Check the server**: it should show `{"ok":true,...}`. If it does, add this website's address to `CLIENT_ORIGIN` on the server. On Vercel, set `VITE_SERVER_URL` to the game server's `https://` address and redeploy. The game server cannot run on Vercel itself.
- **"Connection lost. Reconnecting..." (it was connected):** the app retries automatically and rejoins the same game. If the server restarted or a free host went to sleep, the game is gone (games live in memory); the app says so and returns to the start.
- Free hosts (for example Render's free plan) sleep when idle and lose all games when they wake. Use a paid always-on instance for real events.

## Fixing "The game server address ... is on a serverless host"

That warning means the website and the game server are both on Vercel. Move the game server to Render (one always-on process):

1. Push this folder to GitHub. In Render choose **New > Blueprint**, pick the repository, and apply. `render.yaml` is included and already sets the Node version and `CLIENT_ORIGIN`.
2. When the deploy finishes, open `https://<your-render-address>/health`. You should see `{"ok":true,...}` with an `instance` code and a growing `uptimeSeconds`.
3. **Simplest:** share the Render address itself. It serves the website and the game from one place, so Vercel and the settings below are not needed.
4. **Or keep the Vercel website:** in Vercel, Project Settings, Environment Variables, add `VITE_SERVER_URL` = your Render `https://` address, then redeploy (the value is baked in at build time). In Render, make sure `CLIENT_ORIGIN` lists your Vercel address.
5. Free Render plans sleep when idle and lose all games when they wake. Use a paid always-on instance for a real event and keep it at exactly one instance.

## "Host authorization failed" or "Game not found" in the middle of a game

These mean the server your screen is talking to no longer has the game: it restarted, went to sleep, or you reached a different copy of it. The app now says so ("That game is no longer on the server. The server changed from abc123 to def456...") and returns to the start, instead of leaving a dead game on screen. "Host authorization failed" on its own now only appears for a wrong host token, never after a simple connection drop. To stop it happening, run one always-on server instance (see below).

## "PIN not found" even though the game is running

A game lives in the memory of one server process. If the host and the player connect to different copies of the server (or the server restarted in between), the PIN does not exist where the player landed. This is what happens when the game server runs on Vercel or Netlify, because each request can reach a different copy. It also happens if a host platform runs more than one instance.

- Every running server has a short code, shown as "server abc123" next to "Connected" and in `/health`. **Everyone in one game must show the same code.** If the player's "PIN not found" message names a different code than the host's screen, that is the cause.
- Open `<server address>/health` twice, a few seconds apart. The `instance` code must stay the same and `uptimeSeconds` must keep growing. A changing code or an uptime that resets means several copies or restarts.
- Fix: run exactly one always-on instance of the server (Render, Fly.io, Railway, a VPS) and set `VITE_SERVER_URL` to its `https://` address. The Vercel build now stops if that address ends in `.vercel.app` or `.netlify.app` (set `ALLOW_SERVERLESS_SERVER=1` to override), and the app shows a warning if it is built that way.

## Hosting the website on Vercel (game server elsewhere)

`vercel.json` deploys only the website to Vercel, as a single service called `web`. The game server stays on a host that keeps one long-running process (Render, Fly.io, Railway, a VPS), because the game needs WebSockets and keeps every live game in one process's memory. Vercel Functions start and stop on demand and can run many copies at once, so players could land on different copies with different games. Vercel's WebSocket support is a beta that runs inside a function, with the same limits.

1. Deploy the server first (Render: `render.yaml` is included). Note its address, for example `https://gametribe-live.onrender.com`.
2. On the server host set `CLIENT_ORIGIN` to your Vercel address. Several addresses can be given, comma separated (for example your production domain and your `*.vercel.app` address).
3. In Vercel, import the repository and add the environment variable `VITE_SERVER_URL` set to the server address from step 1 (it must start with `https://`). The build stops with a clear message if it is missing, so the site never goes live without a server to talk to.
4. Deploy. Players open the Vercel address; the QR code and join links use whatever address the host opened.

There are no calls between Vercel services here, so no service bindings are needed: the browser talks to the game server directly.

## Pages and addresses

- `/` home: host a demo quiz, build a quiz, or join a game.
- `/#join` the player page. "Join a game" opens it, the browser back button leaves it, and it can be opened directly.
- `/#join=123456` the same page with the game PIN already filled in (the lobby's QR code and join link use this).
- `/#projector=123456` the read-only projector screen for that game.

## Scoring (documented rule)

- Correct answer: 500 points plus up to 500 for speed (linear over the question time). Wrong or no answer: 0.
- Leaderboard order: score (high to low), then nickname (A to Z). Tied top scores are shown as a tie.

From this directory:


Open the Vite URL shown in the terminal, usually `http://localhost:5173`. Open it in two or more browser tabs to simulate a host and players. Choose a role on each tab. ## Manual reconnect test

1. Start the app with `npm run dev` and create a game in one browser tab.
2. Join from a second tab using a nickname.
3. Start the quiz and submit an answer.
4. Refresh the player tab. It should restore the same player in the active game without asking for the PIN again.
5. Confirm the score and submitted-answer state remain intact. Try to submit another answer for the same question; the server should reject it.
6. Repeat after advancing to another question and after briefly disconnecting/reconnecting the network.

Reconnect data is kept in server memory. Restarting the server clears games and invalidates reconnect tokens. `sessionStorage` is scoped to that browser tab; opening a different tab does not automatically inherit the session.

## Environment

For server settings, copy `server/.env.example` to `server/.env`. For the browser server URL, copy `client/.env.example` to `client/.env`. Vite exposes only variables prefixed with `VITE_` to the browser.

## Security and reliability notes

This is a prototype. Before public deployment, add rate limits, nickname/content validation policy, host-token expiry and rotation, durable storage, structured logs, origin/CORS restrictions, operational monitoring, and abuse protection. The host token is a development credential and should not be treated as a complete production authentication system.
